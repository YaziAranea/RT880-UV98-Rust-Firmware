# Как добавить функцию в прошивку

Рабочий пример R52 — [планировщик APRS](../crates/smart-beacon/src/lib.rs). Он решает, когда нужен следующий пакет, принимает время и готовый `MotionFix` и хранит состояние между вызовами. Прошивка передаёт ему идентификатор выбранного канала и результат отправки. Модулю доступны типы GPS из `uv98-gps-nmea`. Доступ к PTT, несущей и модему остаётся у радиотракта.

## От функции до образа

1. Для независимой функции с собственным состоянием создать крейт `crates/<имя>` с `#![no_std]`. Малую правку существующей функции удобнее оставить в её крейте. Общие типы, кодеки, драйверы и хранилище брать из уже существующих крейтов.
2. Добавить крейт в `members` корневого `Cargo.toml`, зависимость у его потребителя и пакет в список проверок `build-diagnostic-image.ps1`. Обновить `Cargo.lock`. Код функции и тесты используют один публичный API. Настройка размера по умолчанию — `opt-level = "z"`. Для изменения профиля горячего участка нужны отдельные замеры.
3. В точке подключения передать функции данные и обработать результат. Например, решение маяка запросить пакет проходит через существующие проверки канала и обеих PTT. Сигнал об успешном завершении обновляет историю отправки. Проверить модуль отдельно и затем пройти сценарий вместе с его потребителем.

```powershell
cargo test --locked --offline -p uv98-smart-beacon
python tools/build_release.py validation/r53-public
```

Эти команды работают на публичных исходниках. Проверка маяка с радиотрактом использует файл калибровок, описанный в [PRIVATE-INPUTS.md](../PRIVATE-INPUTS.md). Команда этой проверки — `cargo test --locked --offline -p uv98-radio-runtime --test smart_beacon_rf`.

В R53 координация скана зоны и VFO находится в [scan_flow.rs](../firmware-diagnostic/src/scan_flow.rs). Расписание и выбор приоритетного канала использует прежний планировщик. Экранные модули [damage.rs](../crates/handheld-ui/src/damage.rs) и [navigation.rs](../crates/handheld-ui/src/navigation.rs) выбирают строки для обновления и рисуют меню. Их результат проверяется сравнением пикселей с предыдущей версией.

## Бюджет флеша

Последняя команда собирает RU, EN и DE со всеми обычными функциями и показывает стоимость изменения относительно базовой версии **той же локали**. Для каждой сборки измеряется расстояние от конца последнего сегмента, загружаемого во флеш, до начала журнала настроек. Сам журнал занимает отдельные 4096 байт. Длина BIN постоянна из-за заполнения свободной области байтами `FF`.

Минимум перед журналом — **4096 байт в каждом из трёх образов**. Ровно 4096 проходит. Если места меньше, команда сообщает остаток и завершает работу с ошибкой. Готовый каталог с тремя образами появляется после успешной проверки всех языков. Сумма за изменение включает всё, что линкер добавил или удалил вместе с модулем.

Прямой `cargo build` компилирует выбранный профиль. Проверка отдельного ELF — `python tools/check_flash_budget.py <elf> --profile channel-tx --language ru --report <новый-файл.json>`.

В отчёте `flash-budget.json` поле `remaining_flash_bytes` показывает остаток, `flash_cost_vs_baseline_bytes` — расход относительно базы. Положительная дельта означает рост кода. Собственные диагностические профили измеряются отдельно. Если меняется ПО компилятора или параметры сборки, это тоже влияет на дельту. Для оценки одной функции собрать её родительскую ревизию и кандидат тем же инструментарием.

База для сборки R54 хранится в [tools/flash-budget-baseline.json](../tools/flash-budget-baseline.json) и содержит значения выпуска R53. При переходе к следующей версии перенести три значения `remaining_flash_bytes` из отчёта проверенного предыдущего выпуска и указать его имя в `release`. Обновлять базу отдельным коммитом, чтобы история сохраняла точку сравнения.
