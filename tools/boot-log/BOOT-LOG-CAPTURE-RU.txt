Приём раннего журнала UV98 diagnostic 0.1.1

capture_boot_log.py сохраняет только принятые байты. Команд рации, загрузчику,
EEPROM и передатчику в программе нет. Serial-адаптер предоставляет только
read/timeout/close. Этот инструмент сам не устанавливает диагностическую прошивку.
На стоке отсутствие записей UV98D1 ожидаемо и ничего не говорит о запуске будущего
диагностического образа. Проверки этой версии выполнены локально, на fake transport.

Python 3.10+; pyserial нужен только для реального --listen. Декодирование локального
файла, вывод плана и тесты используют стандартную библиотеку Python.

По умолчанию команда только показывает план. COM-порт не открывается, каталог не
создаётся:

    python .\capture_boot_log.py --port COM20 --output .\boot-log-new

Для будущего согласованного испытания с установленным diagnostic 0.1.1:

1. Закрыть CPS, tuning и прошивальщик; порт должен быть свободен. Завершить отдельную
   операцию прошивки до захвата. Захват нельзя совмещать с открытым портом прошивальщика.
2. Оставить USB-кабель подключённым. Выключить рацию.
3. Запустить приём, указав НОВЫЙ каталог:

    python .\capture_boot_log.py --listen --port COM20 --duration 30 --output .\boot-log-new

4. Дождаться строки LISTENING. Только после неё включить рацию без PTT и прочих кнопок.
   Приём уже открыт: это позволяет сохранить самые первые записи после питания.
5. Дождаться завершения 30 секунд; Ctrl+C тоже сохраняет полученные данные и manifest.
   При нескольких перезапусках записи всех стартов остаются в одном rx.bin.

--listen открывает только COM20 с VID=1A86/PID=7523 (CH340). Это проверка адаптера,
не идентификация самой рации. Настройки 115200, 8N1; xonxoff/rtscts/dsrdtr выключены.
DTR и RTS выставляются False до open. Драйвер/USB-адаптер при открытии может менять
состояние физических линий; отсутствие write означает отсутствие отправленных
байтов, а не доказательство отсутствия электрических переходов. Буфер RX не очищается.

Ограничения: длительность 1..120 секунд (по умолчанию 30), RX максимум 128 KiB,
запрос read максимум 1024 байта, буфер незавершённой строки максимум 160 байт между
чтениями. По достижении лимита приём завершается, частичная последняя запись сохраняется.
Повторного открытия, автоисправления и бесконечных попыток нет. Существующий каталог
результата отвергается до открытия COM. На ошибке чтения/закрытия уже принятые данные
сохраняются, статус failed относится к процедуре захвата, не к состоянию прошивки.

Файлы результата:
- rx.bin: полный сырой поток, включая мусор, ACK, неправильные и оборванные записи.
- chunks.jsonl: смещения/длины/контрольные суммы чанков и время получения на компьютере.
- records.jsonl: разобранные записи, причины отклонения, собранный текст ошибки.
- started.json: исходные параметры до открытия порта.
- manifest.json: статус захвата, размеры, SHA-256, ошибки, последний валидный кадр.

Время — время получения чанка хостом; это НЕ таймер MCU. Несколько записей из одного
чанка имеют одинаковое время. Внезапное завершение процесса/потеря питания ПК может
оставить только started.json и частичные файлы; это не завершённый захват.

Офлайн-разбор уже сохранённого rx.bin, без открытия COM:

    python .\capture_boot_log.py --decode .\boot-log-new\rx.bin --output .\boot-log-decoded

Исходный файл остаётся неизменным. Его точная копия сохраняется в новом rx.bin.
Файлы больше 128 KiB отвергаются. У офлайн-разбора нет исходных временных меток;
received_monotonic_ms=null. Исходный chunks.jsonl хранить вместе с захватом.

Протокол UV98D1: ровно 47 ASCII-байт на запись:

    UV98D1 CCCCCCCC AAAAAAAA BBBBBBBB DDDDDDDD*SS\r\n

C — код события u32; A/B/D — три u32 параметра. Цифры hex только 0..9/A..F.
SS — сумма первых 42 ASCII-байт (включая все четыре пробела) по модулю 256.
Пример Rust entry: UV98D1 00000100 00000000 00000000 00000000*12\r\n
Здесь \r\n обозначает реальные CR/LF, а не четыре печатных символа.
Маркер+длина+синтаксис+checksum обязательны. ACK загрузчика и стоковые бинарные кадры
не являются диагностическими событиями. Sum8 обнаруживает часть ошибок передачи;
это не криптографическая аутентификация отправителя.

Текст Rust-ошибки: основной rust_fault содержит A=длина 1..96, B=признак усечения
(0/1), D=0. Затем идут 1F000000|index, index=0..7: по 12 байт ASCII в A/B/D,
каждое u32 little-endian, последний кадр дополнен нулями. Парсер собирает текст
только для непрерывной последовательности индексов после основного fault. Пропуск,
перестановка, неправильный кадр, мусор или новый этап прерывают сборку; complete=false.
Текст без родительского fault остаётся отдельным orphan chunk. Ненулевое дополнение
тоже помечается incomplete. Текст хранится как данные в JSON, не исполняется.

Результат не объявляет рацию исправной/неисправной автоматически. READY означает
только полученный код 0x124; экран, клавиши и сохранность калибровок требуют отдельной
проверки. Последний кадр указывает последнюю наблюдавшуюся точку, но потеря следующего
кадра возможна. Пустой, повреждённый или частичный журнал НЕ доказывает зависание MCU:
возможны позднее начало приёма, неверный UART/baud/pin, проводка, сброс, таймаут TX.

Локальные тесты (никакого COM):

    python -m unittest discover -s . -p test_capture_boot_log.py -v

Тесты проверяют fake-порт, отсутствие TX-метода, настройки до open, таймаут, лимиты,
закрытие/ошибки, точность сырого файла, фрагментацию, checksum, повторы стартов,
частичные записи, восстановление границы кадра и сборку текста ошибки.

Офлайн-интеграция с выводом уже слинкованного ARM-образа из отдельного MMIO-эмулятора:

    python .\verify_boot_log_emulation.py --report ..\uv98-rust-stage\validation\diag-preinit-bootlog-emulation.json --output ..\uv98-rust-stage\validation\boot-log-capture-integration

Проверяются байты UART и четыре u32 каждого сохранённого случая, затем объединённая
последовательность: успешный pre-init, ранняя ошибка, exception, оборванный кадр,
повторный запуск. integration.json сохраняет SHA-256 отчёта и ELF, raw hex и результаты.
Это выполнение ARM-инструкций с подставными MMIO-регистрами и офлайн-разбор, НЕ радио.
Повторный прогон требует новый --output; существующие результаты не перезаписываются.
