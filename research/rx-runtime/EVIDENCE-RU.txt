RX-start, RSSI, статус squelch и нормальный FM audio
2026-11-08. Только статический анализ и bounded Thumb-эмуляция.

Источник и границы
------------------
RT-880_Upgrade_V1_16_250915.nicsure.bin, 251904 байта, base 0x08002800.
SHA256 eaef215cc7084dcd94281bbffb7ab6e2dd1e79ce135f01c90e3dbc691dd16bfc.
https://raw.githubusercontent.com/nicsure/RT880-FlasherX/master/RT-880_Upgrade_V1_16_250915.bin
Это связанный RT880 1.16, не точный MCU readback пользовательской UV98.
В эмуляции доступны только Flash RX и RAM RW. MMIO не отображается.
COM, устройство, прошивка и хостовые EXE не запускались.

1. RX-start: доказанный фрагмент, не полный холодный запуск
--------------------------------------------------------
A: 0x08004FA0, пишет через 0x0801E660.
B: 0x08003E3C, пишет через 0x0801E6D4.
На обоих чипах один порядок:
  W37 = 0x1F0F
  delay8380(10)
  W30 = 0x0200
  W30 = 0xBFF1
Машинные события: rx-start.csv; дизассемблер: rx-start.asm.
Чтения PLL-lock, проверки частоты, готовности или settling здесь нет.
Последовательность не включает нормальную настройку gain/AGC, фильтров,
тонов, AFC, питания, PA-гейтов и общих RF-регистров после reset.
Пригодный автономный RX-only cold-init в этом исследовании не установлен.
Нельзя объявлять подготовленным неизвестное состояние RF после loader.
Сочетание mute -> config plan -> этот start -> ожидание/ack является новой
политикой runtime, а не трассой одной полной штатной функции.

2. Что означает delay8380(10)
----------------------------
0x08008380 делит большие задержки на части; аргумент 10 напрямую передаёт
0x08025224. Инициализация 0x080251EC вызывает 0x0802606C(4), где выставляет
SysTick CTRL.CLKSOURCE (бит 2): источник — core clock.
Затем из clock word RAM[0x20001914] вычисляются:
  us_scale = floor(clock_input_hz / 1_000_000), RAM[0x200010DC];
  ms_scale = us_scale * 1000, RAM[0x200010E0].
Для 10 0x08025224 пишет LOAD = 10 * ms_scale, очищает VAL, включает CTRL.ENABLE,
ждёт COUNTFLAG, снимает ENABLE и снова очищает VAL.
При заявленных 48 MHz машинный LOAD равен 480000. Это номинальные 10 мс,
не 10 циклов и не измеренная задержка. LOAD не уменьшается на единицу;
физическое время зависит от реального clock, SysTick и исполнения кода.
Init использует целое деление частоты, поэтому произвольные clock fractions
не обеспечивают точную шкалу. Рабочая настройка clock — отдельный контракт.

delay-clock.json: выполняет исходные init251EC и delay8380/25224 для
24/48/96 MHz. Перехвачен selector2606C и восемь точных MMIO instructions
2524A,25254,25258,2525E,25266,2527A,25284,25288. COUNTFLAG подаётся сразу.
Это проверка арифметики и запросов регистров, НЕ эмуляция времени SysTick.
Задержка 10 мс не устанавливает PLL-lock или время установления тракта.

3. RSSI первичного A
-------------------
0x08004F40 читает A67, сохраняет u16 и применяет UBFX bits 0..8:
  raw9 = read(A,0x67) & 0x01FF.
Не читает калибровку; не вводит band correction, offset или единицы dBm.
rssi.csv покрывает все 512 нижних кодов с upper bits=0 и upper bits=0xFE00
(1024 входных слова); original helper выполняется целиком.

Отдельный экранный slice 0x08007C3A..0x08007C50 получает тот же raw9:
  magnitude = max(167 - floor(raw9/2), 0).
Строка ROM[0x08007D0C] содержит "RSSI:-000dbm". Это конкретное представление
штатного экрана, не независимая метрологическая калибровка.
Другой consumer 0x0802416A..0x0802418A берёт младший байт raw9 и считает
max(160 - low_byte,0), поэтому единой универсальной формулы dBm по всем
использованиям не заявляем. Runtime полезно выдавать именно raw9.
Срез 7C3A эмулирован до 7C50; результат r7 записан в CSV.

В просмотренных прямых ссылках на reader B 0x0801E698 нет чтения B67.
Сам B-транспорт способен читать регистр, но штатный B RSSI caller и его
нормировка здесь не доказаны. Не переносить A-формулу в B по сходству.
Один успешный read67 не доказывает свежий отсчёт после retune: timestamp,
generation, settling и ack относятся к новому runtime-контракту.

4. Статус squelch
-----------------
Полный helper 0x080051E4:
  if config[0xA4] == 0: return 1;                 // без чтения A0C
  else: return ((read(A,0x0C) >> 1) & 1) | RAM[0x20001120].
Используется бит 1, НЕ бит 4. Значение RAM-флага — целый u8; результат
не обязательно 0/1. При нулевом software override status true означает
(A0C & 2) != 0. Shortcut уровня 0 согласуется со штатным open/off squelch.
Это решение/статус, не непосредственная команда на аудиоусилитель.
Модель нового runtime без RAM[1120] предоставляет аппаратную часть статуса
плюс собственную политику level0; она не воспроизводит весь штатный loop.
squelch-status.csv: 96 сочетаний level0/1/10, flag0/1/80/FF и 8 слов A0C.
Проверяется также число чтений: level0 не обращается к RF.

5. Режим аудио 47, FM и gain 48
-------------------------------
A helper 0x080038AC, B helper 0x08003A08:
  W47 = 0x6040 | ((mode & 0xFF) << 8).
Исходный код заново собирает слово, НЕ делает RMW текущего 47.
mode0 -> 6040; mode1 -> 6140. audio-mode.csv содержит все 256 байт для A/B.
Для runtime оправданы только явно выбранные режимы mute/FM. Остальные
сырые значения в CSV фиксируют арифметику, не разрешают все аудиорежимы.
Команда 6040 закрывает выбранный штатный audio mode; она не доказательство
RF-off, отключения PA или физической тишины при другой аппаратной цепи.

Нормальный FM caller начинается 0x08005098; channel[0]==0 выбирает ветку
0x08005100..0x0800512A. После предыдущей filter/scrambler части он делает:
  input48 = u16(0xB000 + (config[0xAE] << 4) + config[0xAF]);
  W47 = 0x6140;
  read A01;
  W48 = volume_correction(input48, full_reg01).
0x08005768 коррекция:
  full_reg01 ровно 2/3/6/7 И (input48 & 15)>3 -> input48 - 3;
  иначе input48 без изменения.
Сравнивается полный регистр 01: значение 10 НЕ равно режиму 2.
Сами байты config AE/AF — пользовательские коды gain, не измеренная
громкость и не новая калибровка. CPS 1.10 MainForm.cs: numRXSPK.Maximum=63
(строка 6056), numRXDAC.Maximum=15 (5984); загрузка 12293/12294 и сохранение
12816/12817 привязывают их к CFG174/175. Runtime bounds63/15 соответствуют
этому UI. Более широкие raw u8 в oracle проверяют именно арифметику стока.

fm-audio.csv выполняет slice50EA..518E с channel[0]=0 и original05768:
36 наборов AE/AF/reg01, по три события W47/read01/W48. Срез останавливается
перед UI/audio-request проверками. Он не включает предыдущие фильтры,
scrambler и последующий PF8; это не полная настройка звука от reset.
Ранее перенесённая volume_register_05768 проверяется этими же наблюдениями.

6. PF8: полярность запроса звука по машинному потоку
---------------------------------------------------
Схема RT880 V2: U502 physical pin31 = PF8 = AF MUTE. PB11 — другой сигнал
TX29/50M-SW, НЕ mute. См. research/rf-startup/PIN-LABEL-CORRECTION.txt.

RAM u16[0x20001204] — набор запросов аудио:
- helper1FC70(mask) ORs mask и 0x8000;
- normal FM caller в 51BA..51BC вызывает1FC70(4);
- main loop182D0..182DC при flags!=0 пишет0x100 в GPIOF SCR40021418:
  PF8 HIGH, запрос активного аудио;
- helper1F084 при flags==8000 сбрасывает flags=0 и в1F09A пишет0x100 в
  GPIOF CLR40021428: PF8 LOW, активных запросов больше нет.
Перед 182D0 существует RAM[1206] countdown: если он ненулевой, сначала
уменьшается и ветка HIGH в этом проходе пропускается. Не обещаем мгновенное
штатное открытие звука только по OR флага.

Следовательно новый прямой метод set_audio_mute(true) соответствует PF8 LOW;
unmute соответствует HIGH. Это подтверждение полярности штатного запроса,
а не измерение усилителя и физической ревизии UV98.
pf8.json: 18 bounded наблюдений двух веток и 1FC70(4). Перехвачены только
два точных GPIO-store PC; адрес и маска проверяются, MMIO не отображается.
Начальный уровень GPIO, питание и возможность уже активного звука после
loader должны быть явно установлены аппаратным backend/оператором.

7. Повторение и интеграция
-------------------------
  python research/rx-runtime/derive_oracle.py
Опционально UV98_RUST_PROJECT задаёт корень проекта, UV98_STOCK_REFERENCE —
путь к BIN с закреплённым SHA. Требуется Python3 + Unicorn2.1.4; StockArm
берётся из research либо исходного workspace/calibration-analysis.
oracle-summary.json содержит counts, список подмен, ограничения и SHA256
всех CSV/JSON fixture. Ожидаемые значения сняты с Thumb, не вычислены Rust.
Восемь *.asm содержат ограниченные срезы, literal pools остаются данными.

Исследование не добавляет доступ к COM, MMIO или прошивке. Rust runtime,
GPIO backend, fail-stop/rollback, отмена, ownership, тесты и сборка отдельно.
Успех записи команд, таймер или внешний ack сами по себе не подтверждают
чувствительность, качество демодуляции, физический mute либо безопасность
передающего тракта. Здесь доказаны конкретные программные запросы.
