LCD hardware: SPI3, конфигурация и границы доказанного
2026-11-08. Только статический разбор, эмуляция отдельных функций и сборка.
Никаких COM, записи прошивки или обращения к физической рации.

Главный результат
-----------------
Создан opt-in no_std backend uv98-lcd-at32 с PAC AT32F423: SPI3, PA15 CS,
PB3 SCK, PB5 MOSI, PC13 D/C, PC14 RESET. Он реализует uv98_display::DisplayBus.
GPIO-владение разделено через uv98-board-pins::LcdPins; LCD и NOR могут
сосуществовать без копирования GPIOB token. Backlight PA4 и RF не затрагиваются.
Backend не подключён к Stage0/reset entry и не является готовой к прошивке BSP.

Исправление предыдущего вывода: 0x40003C00 — SPI3, не SPI1. В связанном stock
используется AF6. Fagci выбирает SPI1/AF5 на тех же выводах; это другой профиль.
Старый display evidence исправлен; управляющие байты LCD и размеры320x240
остаются прежними, машинный oracle управляющего потока не изменился.

Stock SPI/GPIO: точный ограниченный разбор
-----------------------------------------
Общий init0x080145CC вызывает LCD transport init0x08018064 при0x080145E2,
затем LCD command init0x08017E48 при0x080145FE.
0x08018064..0x0801814A:
  PA15: mux mode2, AF6, push-pull, drive1, no pull.
  PC13/PC14: output mode1, push-pull, drive1, no pull.
  PB3/PB5: mux mode2, AF6, push-pull, drive1, no pull.
  Direct stores0x080180C4/C8: GPIOC CLR0x40020828,0x4000/0x2000.
  SPI3 params0301000000010000: half-duplex TX, master, divisor2,
  MSB-first,8-bit, CPOL1/CPHA0 (mode2), hardware NSS.
  spi_cs_output_enable helper0x08025B44 sets CTRL2 bit2.
  enable helper0x08025B3A sets CTRL1 bit6.
Из reset register state получается CTRL1=C046,CTRL2=4,I2SCTRL=0.
PA15 в аппаратном NSS-режиме; stock LCD command/data routines CS не переключают.

GPIO helpers0x08025464 и0x080254F0 и SPI helper0x08025B7E выполнены в
обычной эмулируемой RAM для4 начальных шаблонов регистров. Все MMIO остаются
unmapped. Внешние вызовы helper перенаправлены в RAM, два прямых stores
проверены по PC/адресу/значению и пропущены. Подмена перечислена в oracle.json.
Результат crates/lcd-at32/tests/fixtures/stock-lcd-init.csv; чужие биты
проверяются отдельно. Это проверка семантики stock кода, не модели GPIO/SPI.

0x08018184 опускает PC13, вызывает data8, поднимает PC13.
0x080181A8 передаёт8bit через0x08025B56 (32-bit store DT+0x0C), затем ждёт
TDBE. У stock нет финального BUSY wait перед сменой DC. Наш backend добавляет
TDBE+BUSY, чтобы возврат DisplayBus означал завершение последнего бита.
RX не используется: half-duplex TX не должен ожидать RDBF.
По stock clock profile APB1 nominal24MHz и divider2 дают nominal12MHz SCK;
это расчёт для связанного BIN, не измерение пользовательской станции.

E7=10: что установлено
----------------------
Даташит p305: SPI2EN bit4 включает режим двух линий данных. Однако p50/62
также требуют IM[3:0]=0101. В этом режиме clock идёт на DCX, данные на SDA
и WRX; p63 описывает9-bit команды с D/C внутри потока, SRAM использует оба
data pin. Для4-line8-bit таблицы p50/55 задают IM=0110 либо1110; отдельная
линия D/C обслуживает8-bit байты (p56).

Связанный stock устанавливает8-bit SPI и отдельный D/C на PC13; его data8
не формирует9-й управляющий бит, data16 использует только MOSI/SDA. Схема
также показывает отдельные D/CX и SCK. Поэтому E7=10 само по себе не означает,
что этот stock тракт стал двухлинейным. Код соответствует4-line byte protocol.
Физические IM внутри модуля и silicon revision неизвестны. Мы не утверждаем,
что datasheet-команда игнорируется на любом4-line контроллере, и не заменяем
её на другое значение без подтверждения. Backend условно применим к модулю,
который поддерживает наблюдаемый stock byte protocol и эту последовательность.

Дополнительное нерешённое соответствие waveform: stock oracle даёт mode2,
а ST7789VW p56 указывает sampling SDA на rising SCL. Названия фаз/слова
конфигурации подтверждены SDK, но электрическая форма сигнала не измерена.
Backend сохраняет stock mode2; переход на mode0 из fagci не сделан молча.
Совместимость реального LCD с этим waveform — явное условие конструктора.

Реализация и отличия от stock
-----------------------------
hardware feature по умолчанию выключена. API:
  unsafe Spi3Lcd<T:BusTiming>::from_quiescent(
      SPI3,LcdPins,&mut CRM,Config,T) -> Self
  Config { divider:Divider,poll_budget:NonZeroU32 }
  BusTiming::wait(TimingPhase::{Setup,Hold,Inactive})
Без default/no-op timing. Caller обеспечивает минимальные интервалы при
известной верхней границе core clock и требованиях своего panel. Отдельный
Display::Delay отвечает за миллисекундные RESET/sleep delays.

Manual CS: PA15 output заменяет AF6, software NSS high вместо hardware NSS;
CTRL1=C346 приdivider2,CTRL2=0. MOSI/SCK остаются AF6. ST7789VW p57 Figure14
показывает допустимый CS-high между целыми командами/параметрами. Наш backend
переключает CS только по границам целых byte slices. Это намеренное отличие,
обеспечивающее явные CS setup/hold/inactive и очистку после ошибки.

Нормальная транзакция: idle wait; DC; CS low; Setup; каждый byte послеTDBE;
финальныеTDBE+BUSY; Hold; CS high; DC high; Inactive. Каждый wait ограничен
poll_budget чтениямиSTS. Любой error: CS high, SPI disable, DC high, Inactive,
terminal Poisoned. После ошибки нет скрытого retry/clocking/reset. Reset не
лечит poisoned transport. Drop прекращает обмен и освобождает CS без RESET.
При abort последний byte может быть обрезан; успешной передачей это не считается.

Конструктор включает только GPIOA/B/C и SPI3 gates, reset только SPI3;
clock tree, backlight, RF/PA и ключи не меняет. CS/DC/RESET preloaded high
перед output mode; unsafe caller уже обязан обеспечить CS inactive/RESET high.
Shared port registers требуют serialized RMW; LcdPins не Send/Sync, но это
не защита от raw aliases, IRQ или unsafe stealing. Пока backends живы,
whole-port reset и конфликтующие CRM/GPIO изменения запрещены контрактом.

Проверка и воспроизведение
-------------------------
derive_lcd_oracle.py повторно создаёт4 seed cases и oracle.json.
Python требует unicorn2.1.4 и matching external BIN в UV98_STOCK_REFERENCE;
UV98_RUST_PROJECT при необходимости задаёт каталог проекта. No MMIO mapped.
  python research/lcd-hardware/derive_lcd_oracle.py
  cargo test -p uv98-lcd-at32
  cargo check -p uv98-lcd-at32 --features hardware --target thumbv7em-none-eabi

12 host tests пройдены в родительской интеграционной сборке; hardware backend
прошёл crossbuild внутри uv98-board-diagnostic. Тесты покрывают oracle/masks,
ordering DC/CS/timing, finite waits, errors/poisoning, reset и Drop cleanup.
Состояние hardware_qualified=false сохраняется. Пины, E7/IM, mode2 waveform,
clock tolerance, power state и реальные LCD timing должны быть подтверждены
до подключения этого backend к загрузочной точке конкретной станции.
