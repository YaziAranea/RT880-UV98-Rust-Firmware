Собственный CPS для UV-98 Plus / RT-880: результат статического разбора

Изучен RT-880 CPS_V1_10_250806.exe, предоставленный пользователем.
Размер 1677824 байта; SHA256:
b2533229c783c86150a4230a8a51c5ee274092e9f1b036bbb7a5b511c34dabd6.
EXE не запускался. COM-порты и рация не использовались. ILSpy 8.2.0 прочитал
сборку статически; блокировки Defender для этого файла не было.

Технология оригинала: .NET Framework 4.0, WinForms, x86; assembly UV_98,
namespace DM550_NOLCD, версия сборки 1.0.0.0. Показанный номер продукта
и имя внутренних классов не являются идентификатором аппаратной ревизии.

Что уже известно о файлах

Файл .880dmf — последовательность пяти сырых буферов. Обработчик сохранения
не добавляет заголовок, номер версии, длины секций или контрольную сумму.
Штатный размер сохранённого файла: 221184 байта, 216 KiB, 0x36000.

  Начало файла  Размер    Буфер     Подтверждённая структура
  0x00000       4096      bufCFG    настройки; пока частично не разобраны
  0x01000       49152     bufAll    1024 записи каналов по 48 байт
  0x0D000       4096      bufFM     отдельные записи FM; полный codec впереди
  0x0E000       32768     bufTime   сохранять непрозрачно до разбора полей
  0x16000       131072    bufZone   256 записей зон по 512 байт

Источник: MainForm.cs, mbtnOpen_Click 13515, mbtnSave_Click 13539;
размеры буферов 2222..2244, каналов 1581, зон 1589.
Имя канала хранится в GBK, до 16 байт (SaveCHName 10944).
Важны байты, а не число Unicode-символов; редактор должен проверять кодировку.

Обычное чтение радио не заполняет bufTime, хотя файл его сохраняет. Поэтому
файл CPS нельзя автоматически назвать свежей полной копией всех этих данных.
Отдельные буферы calibration/GPS/APRS/contacts/images этим файловым обработчиком
не сериализуются. Это не означает отсутствия соответствующих настроек внутри
bufCFG, но означает отсутствие полного бэкапа этих областей в .880dmf.
Внутренняя прошивка MCU и загрузчик в этот формат не входят.

CSV каналов: импорт/экспорт через GBK, 31 колонка, до 1024 строк каналов;
порядок колонок фиксирован, язык заголовков выбирается UI. Поля включают
RX/TX, имя, мощность, сканирование, тоны, полосу и дополнительные коды.
Сток разбивает строку обычным Split(','); корректное CSV-экранирование не
реализовано этим reader. Наличие DMR-полей у общего редактора не доказывает
поддержку DMR конкретной рацией. Для совместимого экспорта ограничивать
неподдерживаемые разделители либо явно предупреждать об их потере.
Источник: ReadCsvColumn 18050, btnCHImport_Click 18070, btnCHExport_Click 18261.

Сравнение с имеющимся UV98 Plus CPS_V1_07_250612

Проверены нормализованные декомпилированные тела 15 методов:
  13 совпадают полностью: транспорт/ответы/checksum, SaveData/DataToPanel,
  кодирование каналов/FM/имён, чтение чисел, CSV import/export.
  mbtnOpen_Click и mbtnSave_Click отличаются только расширением:
  RT880 .880dmf, UV98 .98pdmf.
ReadForm.cs, WriteForm.cs, PortForm.cs, NewFileForm.cs, DesClass.cs совпадают
побайтово между декомпиляциями. Начальные массивы CFG/VFO/APRS тоже совпадают.
Подробности, номера строк и hashes: triage.json; воспроизведение: triage.py.
Это сильная база для общего codec двух файлов, но не доказательство совпадения
всех версий CPS, аппаратных ревизий или всей семантики неизвестных полей.

Покрытие протокола для будущего Rust CPS

  Часть                 Найдено статически                       Статус
  CONNECT/END           34 52 05 10 9B / 34 52 05 EE 79           известно
  Скорость              115200 baud                              известно
  READ                  52, index_hi, index_lo, sum8              известно
  READ response         52, hi, lo, 1024 data, sum8                известно
  CFG                   read blocks 8..11; write opcode 90        запись не тестировали
  Channels              read blocks 16..63; write opcode 91       запись не тестировали
  Zones                 read blocks 112..239; write opcode 92     запись не тестировали
  FM                    read blocks 856..859; write opcode 99     запись не тестировали
  Images                отдельные paths, opcodes 9A/9B            не переносить вслепую
  Clock                 отдельный 14-byte command 2A              отдельно от READ
  Calibration           другой формат/область                     исключить из обычной записи
  MCU firmware/loader   обычный CPS-путь их не читает              не покрыто

READ index — 16-битный номер блока, старший байт первым. Каждый блок 1024 байта.
sum8 — сумма всех предыдущих байтов кадра по модулю 256; ArraySum 10934.
WRITE frame — region opcode, относительный index_hi/index_lo, 1024 data, sum8;
подтверждение 06. Общая длина WRITE/READ response: 1028 байт.
Источник: RevDateOperation 16713 и далее. Обычный READ: 184 блока = 188416 байт.
READ-адреса и WRITE-индексы не взаимозаменяемы: запись адресует свой регион.

Статический разбор отдельного reference firmware показывает условные
сохранения резервных областей на END после операций записи. END нельзя
считать универсально безусловно чистой операцией при неизвестном dirty state.
Здесь никаких кадров не отправляли и восстановление не проверяли.

Предлагаемая архитектура, без привязки UI к протоколу

1. Rust codec: .880dmf/.98pdmf, строгий размер файла, структурные проверки,
   каналы/зоны/FM, GBK, сохранение всех неизвестных и резервных байтов.
   Первый результат — открыть, изменить выбранное поле, экспортировать,
   показать побайтовый diff. Контроль round-trip без изменений обязателен.
2. Версионированная внутренняя модель проекта: явный профиль устройства,
   версия codec, исходный hash, сырые секции и список изменений. Отсутствие
   данных обозначать явно; не заменять непрочитанные области нулями.
3. Протокольная машина состояний отдельно от serial transport и интерфейса.
   Реализовать parser произвольных порций байтов, длину, checksum, адрес эха,
   таймауты и отмену. Не копировать зависимость от ReceivedBytesThreshold,
   Sleep и безусловного DiscardInBuffer из старого WinForms-приложения.
4. План записи формировать отдельно: разрешённые регионы/блоки, ожидаемые
   изменения, предварительный снимок, последующая сверка. Калибровки и
   загрузчик не должны попадать в обычный план изменения каналов.
5. UI: редактор каналов/зон/FM, импорт/экспорт, сравнение с исходным снимком,
   журнал операций. Выбор UI-технологии не нужен для начала разработки codec.
   Общие Rust-библиотеки calibration/stock-model использовать для просмотра
   проверенных калибровочных кодов; это не даёт редактору права менять их.

Ближайший безопасный этап: офлайн-parser и serializer обоих raw-форматов,
тесты lossless round-trip и CSV, затем UI на готовом codec. Связь с радио,
запись и совместимость с будущей собственной прошивкой — отдельные этапы.
Сейчас выполнен только статический triage. UI и serial-компонент не создавались.
