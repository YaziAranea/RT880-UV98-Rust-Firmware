uv98-spectrum: модель последовательного опроса диапазона

Назначение
Пользователь уточнил: нужен график активности диапазона, а не обычный сканер
каналов. Каталог research/scanner сохранён как исходное имя задачи; crate
называется uv98-spectrum. Это новая прикладная политика, не перенос стокового
алгоритма и не доказательство работы спектроанализатора на UV98.

Core: no_std, no allocation, no unsafe, без зависимостей/драйверов/MMIO/COM.
Нет настройки BK4819, включения RX/TX, записи калибровок или перезаписи NOR.
PrepareReceive/TuneReceive/ReadSignal — запросы будущему адаптеру. Сам core
не исполняет их и не выдумывает подтверждения. Передающих действий нет.

Диапазон и данные
Range::new(start_10hz, end_10hz, step_10hz) включает обе границы. Значения
положительны; шаг ненулевой; конец обязан точно лежать на сетке. Максимум
240 bins — ограничение памяти/отрисовки, не предел RF. Все вычисления сетки
проверены до умножения. Поддерживаемые физические диапазоны не угадываются.
Здесь 10 Hz — единица хранения частоты, не размер шага, выбранный за пользователя.
Ни примерный диапазон в тестах, ни representable u32 не разрешают аппаратную
настройку. Допустимость частоты обязан проверить реальный приёмный адаптер.

Каждый bin: latest = None или Measurement{raw:u16,sweep:u64}; peak=None/u16.
raw передаётся без маскировки/перевода в dBm, S-единицы или мощность. Ноль —
действительный полученный код; отсутствие измерения не заменяется нулём.
PeakHold::On хранит численный максимум. Для RF-смысла такого максимума адаптер
должен подтвердить монотонность шкалы. Off не создаёт историю пиков.
ResetPeaks явно очищает только пики; latest сохраняется. Новый проход/Start
сохраняет старые измерения с их исходным sweep, пока новые не получены. UI
обязан различать свежие/старые/отсутствующие точки и показывать остановку/ошибку.

API
Engine::new(Range,Timing,Mode,PeakHold)
Engine::handle(now_ms:u32, Event) -> Option<Action>
Состояние: range(),bins(),sweep(),state(),active_index(),is_running(),ptt_held().

Event: Start, Poll, Ready(ticket), Settled(ticket), Sample{ticket,raw},
Failed{ticket,code}, Stop, Ptt(bool), ResetPeaks.
Action: PrepareReceive{ticket}, TuneReceive{ticket,index,frequency_10hz},
ReadSignal{ticket,index}, SweepComplete{sweep}, Cancel{ticket,reason}.

Последовательность
1. Start выдаёт PrepareReceive и начинает ready_timeout. Start во время
   активного прохода не перезапускает его и не продлевает таймаут.
2. Только Ready с текущим ticket выдаёт TuneReceive для bin0. Адаптер обязан
   подтвердить подготовку RX, допустимость диапазона и отсутствие незавершённой
   операции предыдущего запуска. Ready — не просто истечение задержки.
3. TuneReceive запускает settled_timeout и минимальную задержку settle_ms.
   Только Settled с текущим ticket подтверждает завершение настройки; если
   минимальная задержка ещё не прошла, следующий Poll после неё выдаст ReadSignal.
   Poll без Settled не читает сигнал. settle_ms=0 также требует Settled.
4. ReadSignal получает НОВЫЙ ticket, запускает sample_timeout. Только Sample
   с этим ticket сохраняет raw для нужного bin/прохода. Затем выдаётся запрос
   настройки следующего bin; запросов на TX нет.
5. Последний Sample выдаёт SweepComplete. Mode::Once ждёт нового Start/Ready;
   Mode::Continuous начинает следующий проход только следующим Poll. Один
   вызов не исполняет рекурсивный неограниченный цикл; максимум одно Action.

Билет/ticket уникален во всём сроке жизни Engine, независимо от Stop/Start.
Неверные, повторные и старые ACK/Sample игнорируются, таймаут не продлевается.
Нельзя заменять Engine новым, пока возможны ответы на старые запросы: ticket
уникален в экземпляре, не глобально между разными экземплярами. u64 counters
не оборачиваются: исчерпание отменяет цикл. Engine нельзя клонировать.

Время, остановка, ошибки
Timing::new(ready_timeout,settled_timeout,settle_ms,sample_timeout) без defaults.
Таймауты строго 1..2^31 ms, settle_ms 0..2^31. Интервалы между вызовами активного
Engine должны быть меньше 2^31 ms. Поддерживается wrap u32; обратное или
неоднозначное движение отменяет проход. Remaining time уменьшается saturating,
поэтому серия вызовов через wrap не превращает просроченный deadline в будущий.
При равенстве deadline ответ уже просрочен. Таймаут/текущий Failed приводит к
Cancel, без retry и без сохранения поддельного значения bin.

Stop/PTT(true) отменяют активный проход немедленно, раньше проверки времени.
PTT(true) означает и нажатие, и удержание; блокирует новый Start. PTT(false)
только снимает блокировку, никогда не запускает проход или передачу. Повторный
Stop/held PTT после остановки не создаёт новых команд. Даже после Cancel
late ACK не возобновляет работу. Cancel не утверждает физическое выключение RF,
не восстанавливает предыдущую частоту и не означает подтверждённое завершение
работы адаптера. Без следующего явного Start/Ready новый sweep невозможен.
Once/SweepComplete уже не имеет ожидающих запросов; Stop там не выдаёт команду.

Предел доказательств
Тесты synthetic: ошибки диапазона/таймингов, отсутствие и опоздание ACK,
задержка settle, повторный Poll, сырые крайние коды, continuous/once, peak reset,
старые tickets/partial bins, stop/PTT, u32 wrap, ошибки оборудования, u64 limits.
Они проверяют протокол и данные. Радио, реальный RSSI, скорость обновления,
полоса приёмника, чувствительность и аппаратная совместимость не проверены.
