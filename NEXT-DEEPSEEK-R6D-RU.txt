1. DS-05: Step после PTT текущего слота (ВОСПРОИЗВЕДЕНО CODEX)
crates/handheld-ui/src/controller.rs::select_slot вызывает finish_step_cancel,
но switch_slot при том же слоте немедленно возвращает управление. Экран Step
остаётся открыт без step_before. Следующий UP/DOWN и EXIT сохраняют черновик.
Сценарий: A -> # -> изменить шаг -> PTT A -> release -> изменить шаг -> EXIT.
Независимый тест на распакованном source.zip r6c: FAILED, left 2/right 1,
exit_code 101. До изменения production воспроизвести приложенный тест.
Файлы рядом с этим заданием: r6c-same-slot-regression.patch и .log.
SHA256 исходного r6c source.zip:
4a03c104bfc55ba7ede32f943aa791463fdfa96f1222d2e7b07afd70faa9a563
Исправление: отменённый редактор закрывается либо получает новую корректную
транзакцию; EXIT не сохраняет, MENU — единственный commit. Тесты для A->A,
B->B, A->B, B->A, прямого select_slot, удержания/отпускания и повторного входа.
Не возвращать прежнюю утечку отката A->B. Тест может разрешать оба корректных
UX-решения; не подгонять его под реализацию и не удалять прошлые регрессии.

2. DS-06: Listen показывает не ту частоту и ошибочное состояние звука
Исходники проверены Codex: controller.rs::navigate меняет spectrum_cursor
во время Listen; render.rs берёт крупную частоту по cursor, хотя RF остаётся
на bin, выбранном при начале Listen. Overlay пишет «ЗВУК ВЫКЛ», хотя monitor
открыт. Сделать фактически прослушиваемую частоту отдельным подтверждённым
состоянием либо блокировать изменение курсора во время Listen (наименьшая
корректная правка предпочтительна). Не обозначать выбранный курсор как actual.
Подпись звука зависит от подтверждённого состояния; во время restore не
показывать, что новый сигнал уже слушается. Короткий EXIT из overlay закрывает
overlay; короткий EXIT с Listen возвращает sweep; долгий EXIT/PTT отменяет.
Проверки: Listen bin X -> стрелки/repeat -> MENU/overlay -> EXIT -> EXIT;
фактический RF-план и показанная Listen-frequency остаются согласованы.
Симулятор: Listening, Listening+overlay, Restoring, возврат в sweep.

3. DS-07: проверить смену intent при незавершённом restore
Это ОБНАРУЖЕННЫЙ РИСК ПО КОДУ, пока без воспроизведения Codex, не готовый диагноз.
main.rs Request::ListenSpectrum / AcceptSpectrum допускают scope.active() &&
!scope.listening(), включая Restoring. Новый intent записывается до проверки,
принял ли compact::Engine новый Accept. Engine принимает Accept только running.
Старый Restored(accepted index X) потенциально завершает новый intent для Y.
До исправления создать тест реальной связки request -> scope/engine -> delayed
completion -> action; отдельная таблица spectrum_flow::completion недостаточна.
Сценарии: Listen X -> Accept Y до ACK; Accept X -> Listen Y; повторный Listen;
EXIT/PTT/долгий EXIT при restore; timeout/fault; restart с отложенным ACK.
Если воспроизведётся, привязать intent к принятой операции/идентификатору/bin
или явно отклонять новые действия Busy до смены intent. Отказ не меняет VFO,
не теряет исходный RxRequest и не воскрешает sweep после отмены. Не добавлять
ещё независимых bool без описания переходов. Минимальную логику координации
вынести из main в тестируемый модуль, если без этого реальная гонка не тестируется.
Запуск TX по отменяющему нажатию запрещён существующим release/new-edge guard;
сохранить channel-tx/TOT и обычные разрешённые сценарии передачи.
